# Agent V2 支付故障排查数据

本机 MySQL `agent_v2_incident_lab`，独立于原 `agent_v2_lab`，包含 4,800 笔订单、38,560 条请求日志、6 条发布记录和一张归属标记表。订单和请求日志覆盖北京时间 2026 年 9 月 13 日 18:00—20:00，发布记录包含 17:50 的前置版本。

日志逐条生成请求上下文、路由、连接预算、响应、重试、状态转换和故障调用栈。没有重复字符填充，也没有 `root_cause` 或预期答案字段。一个请求分 8 个阶段，重试使用新的 request_id，同一 order_id 关联不同尝试。

首次本机装载实测：日志正文 34,097,422 bytes（约 32.5 MiB），完整 message 的前 50 行为 43,868 bytes，前 200 行为 175,940 bytes；InnoDB 数据及索引磁盘占用约 69.2 MiB。正文单条为 843—1,272 bytes，大结果来自多条业务记录。

## 准备和核验

复用相邻 `agent-v2-lab/mysql.sh` 中的本机 Docker MySQL 客户端，不输出密码：

```bash
python3 script/test/agent-v2-incident-lab/fixture.py generate
python3 script/test/agent-v2-incident-lab/fixture.py install
python3 script/test/agent-v2-incident-lab/fixture.py verify
```

生成的 SQL 和预期结果默认保存在 `~/Library/Caches/chat2db-tests/agent-v2-incident-lab/`，不提交到 Git。安装只接受不存在的新 schema，拒绝覆盖已有库；数据批次用事务写入。失败时保留现场，不自动删除、重建或绕过检查。`verify` 检查归属、行数、影响订单、最终状态、字节数及全部日志正文 SHA-256。

## 给使用者的正常问题

> 帮我排查 agent_v2_incident_lab 中 9 月 13 日晚上 18 点到 20 点支付失败增多的问题。结合订单、请求日志和发布记录，说明什么时候开始、影响哪些地区和支付渠道、多少订单最终失败，找出最可能的原因，并看看后来是否恢复。给出关键证据和处理建议，只查询，不修改数据。

不向 Agent 指定文件、预览、grep、大小或保存完整性等实现要求。

## 验收者参考

- 18:40 华东 payment-api 发布 1.19.0，连接预算从 800ms 变为 80ms。同期微信通道连接通常需 120—156ms，华东微信首次尝试有 100 单超时，其他地区和渠道可作对照。
- 其中 20 单走稳定连接池重试成功，80 单最终失败。错误日志条数、失败请求数和最终失败订单数不同，不能混算。
- 18:50 回滚至 1.18.4，之后无最终失败订单；订单中共有 4,720 单支付成功，没有重复扣款。
- 18:35 订单缓存发布及后续通知服务/指标服务发布是非因果对照，不能只按时间最近就认定主因。
- 所有明细正文哈希应与生成结果一致。默认 50 行或 200 行日志结果可能触发大结果落盘，但完整文件仅代表该次查询页，不能把分页文件等同全部 38,560 条记录。
- 从真实工具事件判断是否发生落盘、预览外读取及搜索，业务结论正确不自动证明文件链路被覆盖。Agent 合理使用 SQL 聚合或缩小证据范围同样有效，不为强制走文件而改变正常用户问题。

本数据集用于排查大批量有差异的业务记录，原有重复字符串大字段仍保留用于 UTF-8、超长单行和截断边界测试。
